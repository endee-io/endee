This document defines the sparse vector architecture for nDD.

We will use BMW (Band Max-Score WAND) algorithm for sparse vectors. The doc ids will be generated by common id mapper.

The storage will be three MDBX databases

1. docs: It will be a key value store of vectors. key uint64_t(big-endian) will be generated from id mapper. Value will be nnz(uint16)+[term_ids(uint32)]+[values(float16)]. It only be used in delete, update and recreation of index

2. term_blocks: 

   1. key will be term_id(uint32)+start_doc_id(uint64)

   2. Value will be a block of docs (typically 128). The block uses a **Struct of Arrays (SoA)** layout with variable bit-width compression and quantization.

   3. **Header (Version 3)**

      ```cpp
      struct BlockHeader {
          uint8_t version = 3;          // Version 3: SoA layout, uint8 values
          uint8_t diff_bits = 16;       // Compression level: 16, 32, or 64 bits per doc diff
          uint16_t n = 0;               // Total stored (incl. tombstones)
          uint16_t live_count = 0;      // Nonzero entries
          uint16_t padding = 0;         // Explicit padding
          float block_max_value = 0.0f; // Max value in block (used for WAND and dequantization)
          uint32_t alignment_pad = 0;   // Ensures 16-byte alignment for payload
          
          static constexpr size_t HEADER_SIZE = 16; 
      };
      ```

   4. **Data Layout (SoA)**
      
      The compressed payload immediately follows the 16-byte header:

      1. **`doc_diffs` Array**: 
         - Stores `n` integers representing `doc_id - start_doc_id`. 
         - **Variable Width**: The size of each integer is determined by `header.diff_bits`.
           - `16-bit`: used when mostly sequential (block range < 65536).
           - `32-bit`: used for wider ranges.
           - `64-bit`: used only if `idInt` is 64-bit and range exceeds 32 bits.

      2. **`values` Array**:
         - Stores `n` values as `uint8_t` (1 byte).
         - **Quantization**: Values are linearly quantized relative to `block_max_value`.
         - Formula: `stored_val = (real_val / block_max_value) * 255.0`.
         - This reduces memory footprint by 50% compared to Float16 while maintaining sufficient ranking precision.

   5. **Operations**
      - **Adding**: New docs are added to the appropriate block (usually the last one). If a block exceeds `SPLIT_THRESHOLD` (160), it is split into two blocks.
      - **Deleting**: Soft delete by setting value to 0 (tombstone). `live_count` is decremented.
      - **Splitting**: When splitting, tombstones are removed, and data is redistributed to maintain sorted order.

3. term_blocks_index:

   1. It will hold one entry for each term. It will be loaded in RAM and will be synced to LMDB for each changes etc.

   2. It will have information about all the blocks and their block_max_value for all docs in that block. (Header(n u64) + array of (starting_id_of_block, block_max_value)). It is infact a vector of 

      ```C++
      struct BlockIdx {
      uint64_t start_doc_id,
      uint64_t end_doc_id,
      float block_max_value
      }
      ```

      

   3. For each query we will run parallel pointers for each term and will access complete blocks from LMDB. This will also allow us to skip the block altogether.

4. Query:

   1. We will maintain a priority list which will have ids and score. We will use the lowest score in this to traverese in the BMW
   2. For each term we will have a block pointer (fetched from LMDB) and a term pointer (in the RAM)

## Performance Optimizations

### SIMD Acceleration
The implementation uses advanced SIMD instructions to accelerate the "next document" lookup within blocks. The system automatically selects the best available instruction set at compile time:

- **x86_64**:
  - **AVX-512**: Uses 512-bit registers to process 32 (16-bit IDs), 16 (32-bit IDs), or 8 (64-bit IDs) documents per cycle. Enabled via `USE_AVX512`.
  - **AVX2**: Uses 256-bit registers to process 16 (16-bit IDs), 8 (32-bit IDs), or 4 (64-bit IDs) documents per cycle. Enabled via `USE_AVX2`.
- **ARM64**:
  - **SVE2**: Uses Scalable Vector Extensions for variable-length vector processing. Enabled via `USE_SVE2`.
  - **NEON**: Standard 128-bit vector processing (8 x 16-bit or 4 x 32-bit). Enabled via `USE_NEON`.

- **SoA Layout**: The Struct of Arrays layout allows loading `doc_diffs` into vector registers contiguously without interleaving values.
- **Vectorized Search**: `findEntryIndexSIMD` processes multiple document IDs in parallel to quickly locate the first candidate document >= target.
- **Tombstone Skipping**: `findNextLiveSIMD` uses SIMD to efficiently skip over deleted documents (zero values) in the values array.
- **Prefetching**: Explicit data prefetching is used to reduce cache misses during block scanning.

### Runtime Optimizations
- **Pointer-based Sorting**: The WAND algorithm sorts pointers to iterators rather than moving large iterator objects, significantly reducing overhead during the frequent re-sorting steps.
- **Block Skipping**: The system uses block-level max scores to skip entire blocks that cannot contribute to the top-k results.

### Int8 Quantization
- Values are stored as 8-bit unsigned integers (`uint8_t`).
- **Precision**: Sufficient for ranking; values are scaled relative to the block's maximum score (`block_max_value`).
- **Memory**: 50% memory reduction compared to `float16`, 75% compared to `float32`.
- **Speed**: Reduced memory bandwidth usage; dequantization is performed efficiently during scoring using `val * dequant_scale`.

### Variable Bit-Width Compression
- The system automatically chooses the optimal bit-width (16, 32, or 64) for document differences within each block.
- **16-bit Diffs**: Used for dense regions where document IDs are close (diff < 65536).
- **32-bit/64-bit Diffs**: Used for sparser regions or larger ID gaps.
- This results in significantly smaller index size and faster loading times.
